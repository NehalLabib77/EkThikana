# Postgres baseline migration — operator runbook (P0-2)

> **Why this doc exists.** `backend/alembic/versions/20260829080000_initial_commutebd.py` covers only the CommuteBD tables (`places`, `brta_routes`, `metro_stations`, `user_fare_reports`, `crowd_fare_aggregates`, `fare_model_registry`, …). The remaining SQLAlchemy models in `app/database/models.py` (the Phase-2 mirror tables for users / semesters / subjects / tasks / expenses / groups / group_resources) are not yet captured by a committed Alembic revision.
>
> **Operator step (P0-2).** Generate a baseline migration that captures the full ORM, commit it, then apply on Render.

---

## 1. Prerequisites

- Python ≥ 3.11 with the backend dependencies installed (`pip install -r backend/requirements.txt`).
- A throwaway Postgres — local Docker, Neon free tier, or any empty database.
- `DATABASE_URL` exported in the shell where you run `alembic`.

```bash
# Example: local Postgres via Docker
docker run -d --name gochano-pg -p 5432:5432 \
    -e POSTGRES_USER=app -e POSTGRES_PASSWORD=app \
    -e POSTGRES_DB=gochano_postgres_an \
    postgres:16

export DATABASE_URL=postgresql+psycopg2://app:app@localhost:5432/gochano_postgres_an
```

---

## 2. Generate the baseline migration

```bash
cd backend

# Sanity: current revision is the CommuteBD migration, no other committed one
# exists. This is expected — P0-2 fills the gap.
alembic current

# Autogenerate the baseline.  ``--autogenerate`` compares
# ``Base.metadata`` (every imported model in ``app/database/models.py``)
# against the live database and produces a migration that adds every missing
# table / index / constraint.
alembic revision --autogenerate -m "initial-mirror-tables"

# IMPORTANT: review the generated file under
# ``backend/alembic/versions/<timestamp>_initial_mirror_tables.py``.
# Autogenerate is good but not perfect — verify:
#   - No accidental drops (autogenerate only ADDS, but double-check)
#   - All BIGINT primary keys serialised as ``BigInteger().with_variant(Integer(), "sqlite")``
#   - All ForeignKey constraints on the right tables
#   - All CHECK constraints present
```

---

## 3. Test on a throwaway Postgres

Use the CI helper script (delivered with P0-2):

```bash
DATABASE_URL="$DATABASE_URL" \
    python -m scripts.verify_postgres_schema
```

Expected output:

```text
[verify-postgres] running 'alembic upgrade head' in /…/backend
[verify-postgres] expected N tables
[verify-postgres] actual   N tables
[verify-postgres] schema matches SQLAlchemy metadata ✅
```

If the helper reports `MISSING in DB` or `UNEXPECTED in DB`, the autogenerated migration does not match the ORM — fix and re-run.

---

## 4. Roll back if needed

```bash
# Roll back one migration (does not drop the database)
alembic downgrade -1

# Or roll back to nothing (drops every committed migration's objects)
alembic downgrade base
```

---

## 5. Apply on Render (production)

```bash
# On Render shell, with DATABASE_URL already set in the service env:
cd backend
alembic upgrade head
```

Render runs the migration **once per release** at the start of the new container. If the migration is long-running, consider running it manually from the Render shell before deploying the new code.

---

## 6. PostGIS status

The `20260829080000_initial_commutebd.py` migration installs `postgis` and `pg_trgm` extensions but does **not** add `geometry` columns. PostGIS columns are deferred (P4) — the active code uses Haversine on numeric `lat`/`lng`, which is fast enough at the current scale (~10k places). When the dataset crosses 100k rows, switch to `geometry` columns in a new migration.

## 7. Verification

After applying on Render:

```bash
# From Render shell
python - <<'PY'
from sqlalchemy import create_engine, text
from app.core.config import get_settings
engine = create_engine(get_settings().database_url, future=True)
with engine.connect() as c:
    rows = c.execute(text("select tablename from pg_tables where schemaname='public' order by tablename")).fetchall()
    print("\n".join(r[0] for r in rows))
PY
```

Expected: every table from `app/database/models.py` plus `alembic_version`.

---

## 8. Roll-forward safety

- Baseline migration must be **forward-only** (no destructive `downgrade()`).
- If you need to evolve the schema later, create a new migration with `alembic revision -m "<change>"` — never edit the committed baseline.
- All migrations use `op.execute()` for raw SQL when needed, and explicit `op.create_table` / `op.add_column` calls otherwise.
